# 오픈소스 IT 자산 인벤토리 시스템의 Agent + Server + Web FE 아키텍처 조사 (참조 모델)

> 조사 범위: GLPI + GLPI Agent, OCS Inventory NG, Fleet + osquery, Snipe-IT, iTop, Ralph, Rudder, Wazuh syscollector, Tactical RMM / MeshCentral, Microsoft Intune / Configuration Manager.
> 조사 방법 메모: 이 세션은 외부 문서 사이트(readthedocs, learn.microsoft.com, fleetdm.com, wiki.ocsinventory-ng.org 등)로의 직접 접근이 정책상 차단되어 있어, **GitHub raw 소스코드(각 프로젝트의 2026-10 시점 main/develop/master 브랜치)** 를 1차 근거로 삼고, 문서 사이트 내용은 WebSearch 결과 요약(2차 근거)으로 보완했다. 소스코드 인용은 모두 해당 파일을 직접 읽고 확인한 내용이며, 문서 요약 인용은 "(검색 요약)"으로 표시했다. 아래 날짜는 2026-10-11 기준.

## 1. Agent → Server 프로토콜 (transport / 메시지 포맷 / 인증 / 스케줄링 / 압축 / delta / 중복 제거 / 리네임·재설치 처리)

### Takeaway
오픈소스 계열은 크게 두 세대로 나뉜다. (a) OCS/FusionInventory 계보: **HTTP POST + zlib 압축 XML, PROLOG(접촉) → 서버가 주기(PROLOG_FREQ)와 할 일(RESPONSE SEND/STOP)을 지시 → 전체 인벤토리 전송**, deviceid = `호스트명-YYYY-MM-DD-HH-MM-SS` 문자열, 서버 측에서 serial/UUID/MAC/hostname 조합으로 중복 병합. GLPI 11/GLPI Agent는 같은 모델을 **JSON(`action: contact|inventory`, `deviceid`, `GLPI-Agent-ID` UUID 헤더, `application/x-compress-zlib`)** 로 재설계했고 `partial` 인벤토리와 서버 측 룰 엔진(RuleImportAsset: serial/uuid/mac/ip/tag)으로 중복을 제어한다. (b) osquery/Fleet 계보: **TLS + JSON, enroll_secret → node_key 교환, 서버가 쿼리(SQL)를 내려보내고 결과를 올리는 pull 모델**, host_identifier(uuid/instance/hostname) 기반 중복 처리. Tactical RMM/MeshCentral은 상시 연결(NATS over WebSocket / WebSocket)을 쓴다. 자체 ITAM 설계라면 "GLPI JSON 인벤토리 스키마 + osquery식 enroll secret/node key + 서버 측 매칭 룰(serial→uuid→mac)" 조합이 가장 참고할 만하다.

### Cited Findings

**GLPI Agent (구 FusionInventory Agent) ↔ GLPI 11 네이티브 인벤토리**
- GLPI Agent의 `deviceid`는 "호스트명 + 생성 시각"으로 만들어진다. `Agent.pm`: `$data->{deviceid} = sprintf "%s-%02d-%02d-%02d-%02d-%02d-%02d", $assetname, $year+1900, $month+1, $day, $hour, $min, $sec;` 그리고 별도로 `agentid`를 `create_uuid()`로 생성한다. 에이전트 상태는 `vardir`의 persistent storage에 저장되고, `assetname-support` 설정(1=short hostname, 2=as-is, 3=fqdn)이 바뀌면 `normalizeDeviceId()`가 접두 호스트명 부분만 교체해 타임스탬프를 유지한다 — [glpi-agent lib/GLPI/Agent.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent.pm)
- HTTP 클라이언트는 `GLPI-Agent-ID`(UUID) 헤더를 항상 붙이고(유효 UUID가 아니면 전송 거부), `GLPI-Request-ID`, `GLPI-Proxy-ID` 헤더를 사용하며 응답의 `Content-type`이 `x-compress`이면 해제한다. 요청 본문은 `compress()`로 압축된 뒤 POST 된다 — [HTTP/Client/GLPI.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/HTTP/Client/GLPI.pm)
- 압축 선택 로직: `Compress::Zlib` 가능 시 zlib(`Content-type: application/x-compress-zlib`), 아니면 gzip 바이너리(`application/x-compress-gzip`), 둘 다 없으면 무압축. `no-compression` 설정으로 끌 수 있다. OAuth2 Bearer 토큰(`oauth-client-id/secret`)과 `www-authenticate` 처리, `Client-SSL-Warning` 처리 코드가 있다 — [HTTP/Client.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/HTTP/Client.pm)
- CONTACT 메시지: 요청은 `action: "contact"`, `name: "GLPI-Agent"`, `version`, 지원 파라미터 `deviceid, installed-tasks, enabled-tasks, httpd-plugins, httpd-port, tag, tasks`. 서버 응답은 반드시 `status`와 `expiration > 0`을 포함해야 유효하다 — [Protocol/Contact.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Protocol/Contact.pm)
- INVENTORY 메시지: 지원 파라미터 `deviceid action content itemtype partial`, `action => "inventory"`. `partial` 플래그가 있으면 부분 인벤토리 — [Protocol/Inventory.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Protocol/Inventory.pm)
- 공식 JSON 스키마(`inventory.schema.json`)의 최상위 키: `action, content, deviceid, itemtype, jobid, partial, tag`. `content` 하위 섹션: `accesslog, antivirus, batteries, bios, cameras, cartridges, consumables, controllers, cpus, databases_services, drives, envs, firewalls, firmwares, hardware, inputs, licenseinfos, local_groups, local_users, logical_volumes, memories, modems, monitors, network_components, network_device, network_ports, networks, operatingsystem, pagecounters, physical_volumes, ports, powersupplies, printers, processes, remote_mgmt, sensors, simcards, slots, softwares, sounds, storages, usbdevices, users, versionclient, versionprovider, videos, virtualmachines, volume_groups` — [glpi-project/inventory_format inventory.schema.json](https://github.com/glpi-project/inventory_format/blob/master/inventory.schema.json)
- 스키마의 식별 관련 필드: `hardware.uuid`, `bios.ssn`(system serial), `bios.msn`(motherboard serial), `bios.biosserial`, `bios.enclosureserial`, `bios.assettag`, `bios.skunumber`, `bios.secure_boot`, `networks[].mac`, `operatingsystem.hostid` — [동일 스키마](https://github.com/glpi-project/inventory_format/blob/master/inventory.schema.json)
- GLPI JSON 프로토콜 문서(검색 요약): 에이전트 요청은 `action`, `deviceid`(필수), `content`(inventory_format 스키마 준수), `itemtype`(생략 시 `Computer`)을 담은 JSON. 성공 응답은 `status: ok`와 `expiration`; 서버 busy 시 에러를 돌려주고 에이전트는 인벤토리를 보관했다가 재시도 — [glpi-json-protocol inventory](https://glpi-json-protocol.readthedocs.io/en/latest/inventory.html)
- 서버 측(GLPI `src/Glpi/Inventory/Request.php`): "Both XML (legacy) and JSON inventory formats are supported." 액션 상수 `CONTACT_ACTION, INVENT_ACTION, NETDISCOVERY_ACTION, NETINV_ACTION, CONFIG_ACTION`(getconfig), `REGISTER/ESX/COLLECT/DEPLOY/WOL_ACTION`은 코어에서 501("Query ... is not supported") — 플러그인(GLPI Inventory)이 `HANDLE_*_TASK` 훅으로 처리. `GLPI-Agent-ID` 헤더가 있으면 JSON 모드로 전환하고 응답에 `'expiration' => $this->conf->inventory_frequency, 'status' => 'ok'`를 넣는다. 스키마 검증 실패 시 "JSON does not validate" 에러 — [glpi src/Glpi/Inventory/Request.php](https://github.com/glpi-project/glpi/blob/main/src/Glpi/Inventory/Request.php)
- 서버 측 에이전트 식별: `Agent::handleAgent()`는 `glpi_agents.deviceid`로 기존 에이전트를 찾고(`getFromDBByCrit(['deviceid' => $deviceid])`), 없으면 생성. `last_contact`, `useragent`, `version`, `tag`, `port`, `remote_addr`, `enabled-tasks`→`use_module_*` 컬럼을 갱신. 즉 **에이전트(deviceid) 레코드와 자산(Computer) 레코드가 분리**되어 `glpi_agents.itemtype/items_id`로 연결된다 — [glpi src/Agent.php](https://github.com/glpi-project/glpi/blob/main/src/Agent.php)
- 서버 측 중복/연결 룰 엔진 `RuleImportAsset`: 기준(criteria)으로 `entities_id, states_id, model, mac, ip, port description, serial, uuid, OS serial, tag(Agent inventory tag), itemtype, name, partial(Is partial)` 등을 지원하고, 액션은 `_inventory`(Inventory link: `RULE_ACTION_LINK_OR_IMPORT`="Link if possible" / `RULE_ACTION_LINK_OR_NO_IMPORT`="Link if possible, otherwise imports declined") 또는 `_ignore_import`(Refuse import). serial 비교는 길이 4 이상일 때 `LIKE %serial%` 부분 일치도 가능하고, uuid 비교는 `LOWER(uuid)` + VM UUID 바이트 순서 변형(`ItemVirtualMachine::getUUIDRestrictCriteria`)을 고려한다 — [glpi src/RuleImportAsset.php](https://github.com/glpi-project/glpi/blob/main/src/RuleImportAsset.php)
- 룰에 의해 거부된 장비는 `glpi_refusedequipments(name, itemtype, entities_id, ip, mac, rules_id, method, serial, uuid, agents_id, autoupdatesystems_id)`에 기록된다 — [glpi src/RefusedEquipment.php](https://github.com/glpi-project/glpi/blob/main/src/RefusedEquipment.php), [glpi-empty.sql](https://github.com/glpi-project/glpi/blob/main/install/mysql/glpi-empty.sql)
- 비-partial Computer 인벤토리에서 `virtualmachines, remote_mgmt, monitors, antivirus` 섹션이 누락되면 "비어 있음"으로 간주해 기존 연결을 제거한다(즉 full 인벤토리는 상태 교체 의미) — [glpi src/Glpi/Inventory/Inventory.php](https://github.com/glpi-project/glpi/blob/main/src/Glpi/Inventory/Inventory.php)
- 스케줄링: 서버 응답 `expiration`으로 다음 접촉 시각을 정한다(`setNextRunOnExpiration`). 네트워크 오류 시 60초부터 2배씩 늘어나 `delaytime`(기본 3600초)까지 백오프. `lazy=1`이면 예정 시각 전에는 접촉하지 않음 — [Target.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Target.pm), [etc/agent.cfg](https://github.com/glpi-project/glpi-agent/blob/develop/etc/agent.cfg)
- Delta: 에이전트는 full 인벤토리의 체크섬을 `last_state` 파일에 저장하고 `full-inventory-postpone`(기본 14) 만큼 연속으로 변경 없는 경우 전송을 미루거나 partial만 보낸다(`computeChecksum($config->{'full-inventory-postpone'})`), partial 이벤트는 category 단위로 실행되며 "server target for partial inventory events need to be a GLPI server"(GLPI 서버만 partial 지원) — [Task/Inventory.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Task/Inventory.pm), [Config.pm 기본값](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Config.pm)
- 서버가 에이전트 태스크 설정을 내려보낼 수 있다: contact 응답의 `tasks.inventory."no-category"` / `"required-category"`로 수집 카테고리를 원격 제어, 특정 task를 `disabled` 처리 — [Agent.pm getContact](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent.pm)
- 서버 URL 종류: GLPI 11 네이티브(`http://server/`), GLPI Inventory 플러그인(`/glpi/marketplace/glpiinventory/`), 구 FusionInventory 플러그인(`/glpi/plugins/fusioninventory/`) — [etc/agent.cfg](https://github.com/glpi-project/glpi-agent/blob/develop/etc/agent.cfg)

**OCS Inventory NG (Windows Agent 2.x ↔ Communication Server, Perl mod_perl)**
- 프로토콜 흐름(검색 요약, FusionInventory 문서): "The OCS protocol is basically an exchange of XML file done over HTTP(S)"; 에이전트가 먼저 DEVICEID로 PROLOG를 보내고 서버가 파라미터 목록(PROLOG RESP)을 돌려준다; `PROLOG_FREQ`로 다음 접촉 주기를 계산(`PROLOG_FREQ/2 + RANDOM(PROLOG_FREQ/2)`), 미설정 시 기본 3600초 — [FusionInventory agent man page](https://metacpan.org/release/FUSINV/FusionInventory-Agent-2.1.10/view/fusioninventory-agent)
- Windows 에이전트 PROLOG 요청은 `setQuery("PROLOG")`로 QUERY 엘리먼트를 설정하는 `CRequestAbstract` 파생 클래스 — [WindowsAgent OCSInventory Front/PrologRequest.cpp](https://github.com/OCSInventory-NG/WindowsAgent/blob/master/OCSInventory%20Front/PrologRequest.cpp)
- 서버 `_prolog`: 서버는 `hardware` 테이블의 `FIDELITY=FIDELITY+1, QUALITY, LASTCOME=NOW(), USERAGENT`를 갱신하고 `devices` 테이블의 `FREQUENCY`(장비/그룹별 주기 오버라이드)를 조회한 뒤 `PROLOG_RESP_SEND / BREAK / STOP`을 결정한다. 응답 XML의 루트는 `REPLY`이며 `RESPONSE` 값은 `SEND`(인벤토리 보내라) 또는 `STOP`. 응답은 deflate 압축 후 `Content-Type: application/x-compressed`로 전송 — [OCSInventory-Server Communication.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/Communication.pm)
- 세션 추적: PROLOG 시 `prolog_conntrack(DEVICEID, PID, TIMESTAMP)`에 세션을 열고, `SESSION_VALIDITY_TIME` 내에 INVENTORY가 와야 수용(`check_session`), 완료 후 `kill_session` — [Communication/Session.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/Communication/Session.pm)
- 서버 기본 설정(`config` 테이블 초기값): `PROLOG_FREQ=24`(시간), `FREQUENCY=0`, `INVENTORY_DIFF=1`, `INVENTORY_WRITE_DIFF=0`, `INVENTORY_CACHE_ENABLED=1`, `INVENTORY_TRANSACTION=1`, `AUTO_DUPLICATE_LVL=7`, `LOCK_REUSE_TIME=600`, `INVENTORY_ON_STARTUP=1`, `INVENTORY_FILTER_ENABLED=0`, `INVENTORY_FILTER_FLOOD_IP=0`, `IPDISCOVER=2`, `DEPLOY=1`, `DOWNLOAD=0`, `GENERATE_OCS_FILES=0`, `PASSWORD_VERSION=PASSWORD_BCRYPT` — [ocsreports files/ocsbase_new.sql](https://github.com/OCSInventory-NG/OCSInventory-ocsreports/blob/master/files/ocsbase_new.sql)
- Delta 방식: 에이전트가 섹션별 변경 여부를 비트마스크 `CHECKSUM`(HARDWARE, BIOS, MEMORIES, SLOTS, REGISTRY, CONTROLLERS, MONITORS, PORTS, STORAGES, DRIVES, INPUTS, MODEMS, NETWORKS, PRINTERS, SOUNDS, VIDEOS, SOFTWARES, VIRTUALMACHINES, CPUS)로 계산해 `HARDWARE.CHECKSUM`에 실어 보내고, 서버는 `$DATA_MAP{$section}->{mask} & CHECKSUM`으로 변경된 섹션만 갱신(`INVENTORY_DIFF`). 섹션은 기본적으로 "DELETE 후 INSERT"(`delOnReplace`)이며 `INVENTORY_WRITE_DIFF=1`이면 행 단위 diff로 +/-만 적용("more load on frontends, less on DB backend") — [WindowsAgent InventoryRequest.cpp](https://github.com/OCSInventory-NG/WindowsAgent/blob/master/OCSInventory%20Front/InventoryRequest.cpp), [Server Inventory/Update.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/Inventory/Update.pm), [Inventory/Data.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/Inventory/Data.pm), [Map.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Map.pm)
- 중복 처리 두 단계: (1) 에이전트가 deviceid를 바꾼 경우 XML에 `OLD_DEVICEID`를 실어 보내고 서버가 기존 레코드를 교체(`_duplicate_replace`); (2) `AUTO_DUPLICATE_LVL` 비트마스크(`DUP_HOSTNAME_FL, DUP_SERIAL_FL, DUP_MACADDR_FL, DUP_SMODEL_FL, DUP_UUID_FL, DUP_ASSETTAG_FL`)로 hostname / `bios.SSN` / `networks.MACADDR` / `bios.SMODEL` / `hardware.UUID` / `bios.ASSETTAG` 일치를 평가해 기준 마스크를 모두 만족하면 기존 레코드를 대체. `blacklist_macaddresses`, `blacklist_serials` 테이블로 가짜 값(공통 시리얼 등)을 제외 — [Server Duplicate.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/Duplicate.pm)
- Windows 에이전트 로그 예(검색 요약): `DID_CHECK => Read DeviceID <DCKIB01-2017-05-11-15-14-48> and MACs <F2:16:...>` — deviceid는 `ocsinventory.dat`에 저장되며 MAC 목록과 함께 검증된다; PROLOG 응답에 `<RESPONSE>SEND</RESPONSE>`, `PROLOG_FREQ=24`, `INVENTORY_ON_STARTUP` 포함 — [ask.ocsinventory-ng.org 스레드](https://ask.ocsinventory-ng.org/6942/how-got-the-issue-resolved)
- 에이전트 설정 파일(`ocsinventory.ini`) 키(소스 기준): `[OCS Inventory Agent]` 섹션의 `Server, SSL, CaBundle, AuthRequired, User, Pwd, ProxyType, Proxy, ProxyPort, ProxyAuthRequired, ProxyUser, ProxyPwd`(HTTP 기본 인증 + SSL CA 번들), `Debug, Local, NoSoftware, HKCU, NoTAG, IpDisc, ComProvider, WMI_FLAG_MODE, DEFAULT_USER_DOMAIN`; 서버가 PROLOG로 내려준 `PROLOG_FREQ`, `INVENTORY_ON_STARTUP`을 ini의 `[OCS Inventory Service]` 섹션에 다시 써넣는다 — [ComHTTP/HTTPConfig.cpp](https://github.com/OCSInventory-NG/WindowsAgent/blob/master/ComHTTP/HTTPConfig.cpp), [OCSInventory Front/Config.cpp](https://github.com/OCSInventory-NG/WindowsAgent/blob/master/OCSInventory%20Front/Config.cpp), [Agent/OCSInventory.cpp](https://github.com/OCSInventory-NG/WindowsAgent/blob/master/Agent/OCSInventory.cpp)
- TAG(accountinfo): 설치 시 `/TAG:"값"` 또는 사용자 입력 대화상자(`/NOTAG`로 생략)로 `admininfo.conf`에 기록되고 서버 `accountinfo(HARDWARE_ID, TAG)`에 저장; 서버가 `ACCOUNT_UPDATE` 응답으로 TAG를 다시 내려줄 수도 있다(에이전트 재설치 시 `TAG=LOST`) — [Agent/OCSInventory.cpp](https://github.com/OCSInventory-NG/WindowsAgent/blob/master/Agent/OCSInventory.cpp), [Server Inventory.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/Inventory.pm)

**osquery (TLS remote API) + Fleet**
- 인증/등록: 노드는 `--tls_hostname`, `--enroll_tls_endpoint`에 `enroll_secret`(파일 `--enroll_secret_path` 또는 env `--enroll_secret_env`) 또는 TLS client cert(`--tls_client_cert/--tls_client_key`)를 제출하고 `node_key`를 받아 RocksDB에 저장한다. 이후 config/logger/distributed 요청마다 `node_key`를 보낸다. 서버 CA 핀닝은 `--tls_server_certs`. 등록 요청 본문: `{"enroll_secret","host_identifier","host_details":{"os_version":{},"osquery_info":{},"system_info":{},"platform_info":{}}}`, 응답 `{"node_key","node_invalid"}` — [osquery docs/wiki/deployment/remote.md](https://github.com/osquery/osquery/blob/master/docs/wiki/deployment/remote.md)
- 설정 요청은 POST `{"node_key","etag"}`, 응답은 `schedule`(query_name → {query, interval}) 등 설정 JSON; 변경 없으면 `{"etag":"ok"}`로 응답 가능(조건부 요청). 로거 요청은 `{"node_key","log_type":"result|status","data":[...]}`. 분산 쿼리(ad-hoc)는 `distributed/read`(`{"queries":{"id":"SELECT ..."},"discovery":{...}}`) / `distributed/write`(`{"queries":{"id":[rows]},"statuses":{"id":0}}`). 등록 후 모든 요청에 `Authorization: NodeKey <node_key>` 헤더도 포함. TLS 1.2만 지원, Boost.Beast + 정적 OpenSSL, UA `osquery/X.Y.Z` — [동일 remote.md](https://github.com/osquery/osquery/blob/master/docs/wiki/deployment/remote.md)
- 오프라인/버퍼링: 로거 엔드포인트가 응답하지 않으면 RocksDB에 버퍼(`--buffered_log_max=1000000`, 초과 시 오래된 것부터 삭제). `--logger_tls_period=3`초 간격으로 최대 `--logger_tls_max_lines=1024`줄, 줄당 `--logger_tls_max_linesize=1048576`(1MB) 전송. 압축은 `--logger_tls_compress=false`(GZIP, 기본 off). 등록 재시도 `--tls_enroll_max_attempts=12`, 지수 백오프 상한 `--tls_enroll_max_interval=600`. 설정 갱신 `--config_refresh=0`(기본은 시작 시 1회), 실패 시 `--config_accelerated_refresh=300`. `--distributed_interval=60`. `--host_identifier=hostname|uuid|ephemeral|instance|specified`(`--specified_identifier`) — [osquery cli-flags.md](https://github.com/osquery/osquery/blob/master/docs/wiki/installation/cli-flags.md)
- Fleet 서버의 등록 처리(`EnrollOsquery`): `host_details.system_info`에서 `uuid`(hardware UUID)와 `hardware_serial`을 추출하고, `getHostIdentifier()`가 서버 설정(`provided|instance|uuid|hostname`)에 따라 `osquery_info.instance_id` / `osquery_info.uuid` / `system_info.hostname` 중 하나를 호스트 식별자로 고른다. 서버가 `node_key`를 랜덤 생성(`NodeKeySize`)하고 `WithEnrollOsqueryHostID/HardwareUUID/HardwareSerial/NodeKey`로 호스트를 upsert. 일회용 enroll secret은 `MatchesHost(platform, hardwareUUID, hardwareSerial)`로 특정 장비에 묶인다. orbit(fleetd)은 별도의 `orbit_node_key`로 인증(`LoadHostByOrbitNodeKey`) — [fleet server/service/osquery.go](https://github.com/fleetdm/fleet/blob/main/server/service/osquery.go)
- Fleet `hosts` 테이블 컬럼: `osquery_host_id, node_key, hostname, uuid, platform, osquery_version, os_version, build, platform_like, code_name, uptime, memory, cpu_type, cpu_subtype, cpu_brand, cpu_physical_cores, cpu_logical_cores, hardware_vendor, hardware_model, hardware_version, hardware_serial, computer_name, primary_ip, primary_mac, distributed_interval, logger_tls_period, config_tls_refresh, label_updated_at, last_enrolled_at, refetch_requested, team_id, policy_updated_at, public_ip, orbit_node_key, last_restarted_at, timezone` 등 — [fleet server/datastore/mysql/schema.sql](https://github.com/fleetdm/fleet/blob/main/server/datastore/mysql/schema.sql)

- Fleet agent options: `config.options`(예 `distributed_interval: 3`, `distributed_tls_max_attempts: 3`, `logger_tls_endpoint: /api/osquery/log`, `logger_tls_period: 10`)는 재시작 없이 적용, `command_line_flags`는 fleetd 재시작 시 적용. `host_identifier`와 `database_path`는 fleetd가 관리하므로 설정 불가. `decorators`(load/always/interval)로 결과 로그에 `host_uuid`, `username` 등을 첨부. 구 enroll secret을 폐기하면 그 secret으로 등록된 호스트는 새 flags를 못 받는다 — [fleet docs/Configuration/agent-configuration.md](https://github.com/fleetdm/fleet/blob/main/docs/Configuration/agent-configuration.md)

### Inferences
- 두 계보의 핵심 차이는 "에이전트가 스키마를 알고 전체 문서를 보내는가(OCS/GLPI)" vs "서버가 SQL을 내려보내 필요한 것만 받는가(osquery/Fleet)"이다. 자체 ITAM(C# 에이전트)에서는 전자가 구현이 단순하고 오프라인 캐시/전송 재시도도 쉽다. 후자의 장점(서버 측에서 수집 항목 변경)은 GLPI의 `no-category/required-category` 원격 설정과 TRMM의 레지스트리 체크인 주기 오버라이드처럼 "서버가 카테고리/주기를 내려주는" 방식으로 상당 부분 흡수 가능하다.
- 장비 식별은 세 계층으로 분리하는 것이 공통 패턴이다: (1) 에이전트 설치 인스턴스 ID(GLPI `agentid` UUID, osquery `instance_id`, TRMM `AgentID`), (2) 에이전트가 주장하는 deviceid(호스트명+시각), (3) 서버가 하드웨어 지문(serial → BIOS/SMBIOS UUID → MAC → hostname/model)으로 자산을 매칭하는 룰. GLPI/OCS 모두 "에이전트 레코드"와 "자산 레코드"를 분리해 재설치·리네임 시 에이전트만 바뀌고 자산은 유지되게 했다.
- OCS의 `OLD_DEVICEID`와 GLPI의 `normalizeDeviceId`는 "호스트명이 바뀌어도 타임스탬프 부분은 유지"하는 식으로 리네임을 추적한다. 재이미징은 deviceid가 완전히 새로 생기므로 결국 서버 측 serial/UUID 매칭 룰에 의존한다 — 블랙리스트(OCS `blacklist_serials/macaddresses`, GLPI "Refuse import" 룰)가 필수다.
- 압축은 zlib/deflate(OCS, GLPI) 또는 gzip(osquery 선택)으로 단순하며, 모두 HTTP 본문 압축 수준이다. 자체 구현에서는 `Content-Encoding: gzip` 표준 헤더 + JSON으로 충분하다.

### Gaps
- GLPI Agent 공식 문서(readthedocs)와 glpi-json-protocol 문서의 원문은 네트워크 차단으로 직접 확인하지 못했고(검색 요약만 사용), `AbstractRequest::DEFAULT_FREQUENCY`의 실제 값(시간 단위 기본 주기)도 파일을 못 받아 확인하지 못했다.
- OCS Windows 에이전트가 deviceid를 생성/검증하는 정확한 코드(`DeviceID.cpp`)는 경로를 찾지 못해 로그 예시로만 확인했다.
- MeshCentral의 agent↔server 핸드셰이크(인증서 해시 기반 NodeID 생성 규칙)와 인벤토리 메시지 스키마는 설계 PDF/소스를 직접 읽지 못해 미확인.
- Fleet의 소프트웨어 타이틀 정규화/CPE 매칭 세부와 Fleet 공식 "host identifier" 문서는 검색 한도 소진으로 미확인.

## 2. Windows에서 에이전트가 수집하는 항목과 수집 방법 (WMI / 레지스트리 / Win32 API / osquery 테이블), 소프트웨어 정규화, 로그인 사용자, 모니터(EDID), 프린터, USB, 백신, 업데이트, BitLocker, 배터리, 사용량 미터링

### Takeaway
모든 에이전트가 사실상 같은 Windows 데이터 소스를 쓴다: 소프트웨어는 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` + `Wow6432Node` + `HKEY_USERS\<SID>\...\Uninstall`(DisplayName/DisplayVersion/Publisher/InstallDate/UninstallString/SystemComponent/NoRemove) 및 AppX(`Get-AppxPackage`/PackageFamilyName), 핫픽스는 `Win32_QuickFixEngineering`(또는 레지스트리), 하드웨어 식별은 `Win32_Bios.SerialNumber`, `Win32_ComputerSystemProduct.UUID`, `Win32_SystemEnclosure.SerialNumber/SMBIOSAssetTag`, `Win32_BaseBoard.SerialNumber`(Wazuh는 `GetSystemFirmwareTable("RSMB")`로 SMBIOS 직접 파싱), 모니터는 레지스트리 `Enum\DISPLAY\...\Device Parameters\EDID`(또는 `EDID_OVERRIDE`) 파싱, 백신은 `root\SecurityCenter2` `AntiVirusProduct.productState` 비트 해석 + 벤더별 CLI, BitLocker는 `Win32_EncryptableVolume`, 배터리는 `powercfg /batteryreport /xml`, 마지막 로그인 사용자는 `explorer.exe` 프로세스 소유자(`Win32_Process.GetOwner`) 또는 `Authentication\LogonUI\LastLoggedOnUser`. 소프트웨어 정규화는 에이전트가 아니라 서버 룰(GLPI 소프트웨어 사전, OCS `dico_soft`/software_name·publisher·version 정규화 테이블, Fleet `software_titles`)에서 한다. 사용량 미터링은 조사 대상 오픈소스에는 ConfigMgr 수준의 기능이 없고, Fleet가 prefetch 기반 `last_opened_at`만 제공한다.

### Cited Findings

**GLPI Agent — Win32 모듈별 수집 방법**
- WMI 접근은 Perl `Win32::OLE`로 `winmgmts:{impersonationLevel=impersonate,(security)}!//./` 모니커를 열어 질의하며(`getWMIObjects`), 레지스트리는 `Win32::TieRegistry` + `getRegistryValue/getRegistryKey`, UTF-16LE 디코딩, 사용자 하이브 로드(`loadUserHive`), PowerShell 실행(`runPowerShell`), `root/StandardCimv2`와 `Root/Microsoft/Windows/RemoteAccess/Client`(VPN) 네임스페이스도 사용. 에이전트 메모리 측정(`getAgentMemorySize`)과 OLE 워커 프로세스 분리(`start_Win32_OLE_Worker`) 코드가 있다 — [Tools/Win32.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Tools/Win32.pm)

- C#/.NET 에이전트에서 그대로 옮길 수 있는 "검증된 소스 매핑": 소프트웨어(레지스트리 3경로 + AppX + MSI UpgradeCode), 핫픽스(`Win32_QuickFixEngineering`), 식별자(`Win32_Bios/ComputerSystemProduct/SystemEnclosure/BaseBoard` + SMBIOS 직접 파싱 fallback), 모니터(EDID 레지스트리 파싱 + "Surface Display" 제외), 백신(`SecurityCenter2.productState` 비트), BitLocker(`Win32_EncryptableVolume`), 배터리(`powercfg /batteryreport`), 로그인 사용자(`explorer.exe` 소유자 + `LastLoggedOnUser`). 이들은 세 프로젝트(GLPI/osquery/Wazuh) 이상에서 동일하게 쓰이므로 안전한 선택이다.
- 소프트웨어 노이즈(Publisher 표기 편차, 버전이 이름에 포함, 32/64비트 중복, SystemComponent=1 숨김 항목)는 에이전트에서 raw로 보내고 **서버 측 정규화 테이블(name/publisher/version 분리) + 룰 기반 사전 + "replay"** 로 처리하는 것이 OCS/GLPI/Fleet의 공통 설계다. GLPI는 `transliterator_transliterate("Any-Latin; Latin-ASCII; ...")` + `mb_strtolower`로 제조사 키를 정규화한 뒤 md5 키로 비교한다(Software.php 참조).
- 사용량 미터링은 ConfigMgr 소프트웨어 미터링 외에는 오픈소스에서 거의 구현되지 않았고, Fleet의 prefetch 기반 `last_opened_at`이 유일한 근사치다. 자체 구현 시 prefetch(`C:\Windows\Prefetch`) 또는 ETW/`Win32_Process` 폴링을 고려해야 하며 이는 별도 설계가 필요하다.

### Gaps
- Fleet의 Windows `software_windows` 쿼리 본문 전체와 CPE/CVE 매칭 정규화 규칙은 확인하지 못했다(검색 한도 소진).
- Intune Device Inventory의 속성 카탈로그 전체 목록(예: Battery/TPM/EncryptableVolume/Qfe 카테고리 명세)과 ConfigMgr 공식 문서 원문은 learn.microsoft.com 접근 불가로 2차 자료로만 확인했다.
- MeshCentral의 소프트웨어 인벤토리 수집 방식(어떤 레지스트리/WMI를 쓰는지)은 미확인.

## 3. 에이전트 패키징과 라이프사이클 (서비스 vs 스케줄 작업, MSI/GPO 배포, 자체 업데이트, 설정 저장 위치, 프록시, 오프라인, 리소스)

### Takeaway
GLPI Agent는 MSI(`msiexec /i ... /quiet SERVER=... EXECMODE=1|2|3 TAG=... RUNNOW=1`)로 배포되며 설정을 `HKLM\SOFTWARE\GLPI-Agent`에 저장하고 Windows 서비스(`glpi-agent`) 또는 Task 모드로 실행, 내장 HTTP 서버(62354)로 서버가 깨울 수 있다. OCS Windows Agent는 NSIS 설치 + `ocsinventory.ini`, 서비스 모드/`/NO_SERVICE`, OCS 서버의 Deployment 기능 또는 GPO로 배포. Fleet는 fleetd(orbit)가 osqueryd를 감싸 **TUF 기반 자동 업데이트**(기본 tuf.fleetctl.com, Premium은 자체 TUF)와 flags 원격 관리를 담당. Tactical RMM은 Inno Setup 설치본 + `kardianos/service` Windows 서비스 + 레지스트리 설정 + 서버 지시 자체 업데이트(`AgentUpdate(url, inno, version)`). MeshCentral 에이전트는 `.msh` 설정과 서버 푸시 자체 업데이트(`disableUpdate`로 차단 가능). 모든 에이전트가 HTTP 프록시 옵션을 가진다. 오프라인 시 GLPI/OCS는 다음 접촉까지 로컬 보관(백오프), osquery는 RocksDB 버퍼.

### Inferences
- 자체 C# 에이전트 설계에 바로 쓸 수 있는 조합: (1) MSI + 설치 속성(SERVER/TAG/RUNNOW/EXECMODE) + GPO/Intune Win32 배포, (2) `HKLM\SOFTWARE\<Vendor>-Agent` 레지스트리 설정(서버가 PROLOG/contact 응답으로 일부 값을 덮어쓰는 OCS/TRMM 패턴), (3) Windows 서비스 상시 실행 + 서버 지시 주기, (4) 자체 업데이트는 "서버가 버전·URL·해시를 내려주고 에이전트가 MSI를 받아 재실행"(TRMM 방식)이 가장 단순하며, 공급망 보호가 필요하면 Fleet의 TUF 모델을 참고.
- 오프라인 처리는 "마지막 인벤토리/체크섬을 로컬에 저장하고(GLPI `last_state`, OCS `.ocs` 로컬 파일), 서버 복구 시 재전송 + 지수 백오프"가 표준이다.
- 리소스 측면에서 GLPI Agent(Perl + Win32::OLE)는 OLE 워커 프로세스 분리와 메모리 측정 코드가 있을 정도로 메모리 관리가 과제였고, osquery는 watchdog으로 200MB/10% 상한을 강제한다. .NET 에이전트도 WMI 쿼리의 COM 누수 및 장시간 실행 메모리 상한(예: watchdog 재시작)을 설계에 포함할 가치가 있다.

### Gaps
- GLPI Agent MSI의 전체 속성 목록(`ADD_FIREWALL_EXCEPTION`, `TASK_FREQUENCY`, `HTTPD_*` 등)은 공식 문서를 직접 읽지 못해 확인하지 못했다.
- OCS Agent Deployment Tool(원격 설치 도구)과 OCS 공식 GPO 절차는 wiki 접근 불가로 미확인.
- Tactical RMM/MeshCentral의 실제 메모리/CPU 사용량 수치는 1차 자료를 찾지 못했다.

## 4. 서버 데이터 모델 (컴퓨터/컴포넌트/소프트웨어+버전/라이선스/사용자/위치/상태/라이프사이클/이력) — GLPI 모델과 import 룰 엔진 중심

### Takeaway
GLPI는 "자산(glpi_computers, glpi_assets_assets[GLPI 11 generic asset]) — 컴포넌트(glpi_device*/glpi_items_device*) — 소프트웨어(glpi_softwares → glpi_softwareversions → glpi_items_softwareversions) — 라이선스(glpi_softwarelicenses → glpi_items_softwarelicenses) — 계약(glpi_contracts_items) — 티켓(glpi_items_tickets)" 구조에 `is_dynamic`(에이전트 유래) 플래그, `glpi_lockedfields`(필드 잠금), `glpi_logs`(변경 이력), `glpi_agents`(에이전트 레코드), `glpi_rules/rulecriterias/ruleactions`(import/dictionary 룰), `glpi_refusedequipments`, `glpi_unmanageds`를 더한 모델이다. OCS는 `hardware`(DEVICEID, LASTDATE/LASTCOME, CHECKSUM, QUALITY/FIDELITY, UUID)를 중심으로 섹션별 테이블(`bios, software, networks, monitors, storages, memories, cpus, videos, printers, drives, registry, virtualmachines, batteries, usbdevices`)이 `HARDWARE_ID`로 매달리고, `accountinfo(TAG)`가 수동 관리 속성 확장점이다. Fleet는 `hosts` + `software/software_titles/host_software` + 취약점(`software_cpe/software_cve`) + 정책/라벨 중심이며 ITAM적 라이프사이클(구매/상태/할당)은 없다. Snipe-IT/Ralph는 반대로 라이프사이클·할당·감가상각·라이선스 중심이고 기술 인벤토리가 없다.

### Inferences
- MS SQL 기반 자체 모델을 설계할 때 GLPI의 세 가지 분리가 가장 중요하다: (1) `agents`(deviceid, last_contact, version, tag, remote_addr) vs `computers`(serial, uuid, otherserial(asset tag), states_id, locations_id, users_id, is_dynamic), (2) 소프트웨어 카탈로그(`softwares`)와 버전(`softwareversions`)과 설치 연결(`items_softwareversions`, `date_install`, `is_dynamic`), (3) 라이선스(`softwarelicenses.number`, `softwareversions_id_buy/_use`, `expire`, `allow_overquota`)와 라이선스-장비/사용자 연결. 여기에 `lockedfields`, `refusedequipments`, `rulematchedlogs`, `logs`를 더하면 "에이전트 데이터 vs 수동 데이터 조정" 요구가 충족된다.

## 5. 따라 할 만한 FE 기능 (목록+저장 검색, 상세 탭, 소프트웨어 카탈로그·설치 수, 라이선스 컴플라이언스, 에이전트 vs 수동 데이터 조정, 대시보드)

### Takeaway
확인된 1차 자료 기준으로 베낄 가치가 큰 것은 GLPI의 (a) 에이전트/잠긴 필드/거부 장비 세 메뉴, (b) 자산의 "Import Information" 탭(어느 룰이 생성/갱신했는지), (c) 룰 재생(Replay), (d) 소프트웨어 사전; Fleet의 (e) 소프트웨어 타이틀별 호스트 수 집계 테이블(`software_titles_host_counts`)과 취약점 수 집계(`vulnerability_host_counts`), (f) 라이브 쿼리/정책(pass/fail) 뷰; Snipe-IT의 (g) 체크아웃/체크인/감사(audit) 워크플로와 EOL/보증 날짜; Ralph의 (h) 상태 전이(TransitionField) 워크플로; Wazuh의 (i) IT Hygiene 대시보드와 인벤토리 리포트 생성. 단, FE 화면 자체에 대한 1차 문서는 접근 제한으로 충분히 확인하지 못했다.

- 라이선스 컴플라이언스는 GLPI 모델(`number` 보유 수 vs `items_softwarelicenses` 할당 수, `allow_overquota`, `expire`) + Ralph의 사용자/코어 단위 할당 개념을 합치면 충분하다.

### Gaps
- GLPI/OCS/Snipe-IT/Ralph/iTop의 실제 화면(저장 검색, 컴퓨터 상세 탭 구성, 대시보드 위젯)에 대한 공식 문서/스크린샷은 접근 제한으로 확인하지 못했다. GLPI "saved searches"와 대시보드(GLPI 9.5+) 기능은 알려져 있으나 이번 조사에서 1차 출처를 확보하지 못했다.

## 6. 알려진 약점·불만 (대규모 성능, XML 오버헤드, 중복 장비 등)

### Takeaway
공통 불만은 (1) 중복 장비(호스트명/UUID/시리얼 기준 룰 설정 실수, 복제 VM, 공통 시리얼), (2) 대규모에서 DB 병목(OCS는 10,000대 이상에서 서버 분리 권고, MySQL `max_connections` 100 제한; GLPI는 `wakeupagents` 락 오류·태스크 로그 누적; Fleet는 MySQL/Redis 스케일링 전제), (3) OCS/구 GLPI의 XML+Perl mod_perl 스택의 노후화(GLPI 11이 JSON으로 전환한 배경)다. Snipe-IT/Ralph/iTop는 에이전트가 없어 기술 인벤토리를 외부(OCS/GLPI/Jamf/Rudder)에서 가져와야 한다.

### Cited Findings
- OCS 공식 가이드(검색 요약): "above 10000 inventoried computers, we recommend using at least 2 physical servers"(DB+통신 서버 / DB 레플리카+관리·배포 서버 분리); Communication Server는 Apache 2.2/2.4의 Perl 모듈; MySQL 기본 100 동시 접속 제한으로 통신 서버가 굶을 수 있어 `max_connections` 상향; 70,000 클라이언트 운영 사례는 레플리카로 콘솔 쿼리 분리 — [OCS wiki 서버 설치](https://wiki.ocsinventory-ng.org/03.Basic-documentation/Setting-up-a-OCS-Inventory-Server/), [OCS wiki Management server tuning](https://wiki.ocsinventory-ng.org/09.Extras/Management-server-tuning)
- OCS 커뮤니티(검색 요약): 약 3,800대에서 "All computers" 페이지가 수 분 걸림; Perl 모듈의 `DBD::mysql rollback` 경고 다수; `memories` 테이블 크기로 검색 지연 — [ask.ocsinventory-ng.org 3825](https://ask.ocsinventory-ng.org/3825/extremely-slow-performance-on-all-computer-page), [ask.ocsinventory-ng.org 3519](https://ask.ocsinventory-ng.org/3519/ocs-inventory-ridiculously-slow)
- OCS 서버에는 인벤토리 폭주 방지 옵션 `INVENTORY_FILTER_FLOOD_IP`, `INVENTORY_FILTER_FLOOD_IP_CACHE_TIME=300`, `PROLOG_FILTER_ON`, 장비 락(`locks`, `LOCK_REUSE_TIME=600`)이 있다 — [ocsbase_new.sql](https://github.com/OCSInventory-NG/OCSInventory-ocsreports/blob/master/files/ocsbase_new.sql), [System.pm](https://github.com/OCSInventory-NG/OCSInventory-Server/blob/master/Apache/Ocsinventory/Server/System.pm)
- GLPI(검색 요약): 10.0.1 네이티브 인벤토리 전환 후 웹 UI에서 에이전트 액션 실행 시 `wakeupagents` 크론이 "cannot recover the lock on the DB"로 실패·프리즈; 네트워크 디스커버리 동시 스레드가 많으면 서버/네트워크 부하 — [GLPI 포럼 284322](https://forum.glpi-project.org/viewtopic.php?id=284322), [GLPI FAQ(fr)](https://help.glpi-project.org/faq/fr/plugins/glpi-inventory)
- GLPI 중복(검색 요약): import 룰 순서 실수("Computer import (by serial + uuid)"가 먼저 매칭되어 신규 생성), 룰 삭제 시 매 인벤토리마다 새 장비 생성, 시리얼 없는 VM은 UUID 전용 룰 필요, 올인원 PC 내장 모니터가 별도 모니터로 생성 — [GLPI 포럼 288527](https://forum.glpi-project.org/viewtopic.php?id=288527), [35282](https://forum.glpi-project.org/viewtopic.php?id=35282), [pid=149694](https://forum.glpi-project.org/viewtopic.php?pid=149694), [283904](https://forum.glpi-project.org/viewtopic.php?id=283904)
- GLPI Agent 코드 주석: `Win32_DesktopMonitor`는 두 번째 모니터를 놓칠 수 있고 "Surface Display"가 잘못된 시리얼을 노출; `Win32_PerfRawData_Tcpip_NetworkInterface`는 MAC/GUID 연계 속성이 없어 매칭이 어려움; AppX PowerShell 스크립트 8000자 제한 — [Generic/Screen.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Task/Inventory/Generic/Screen.pm), [Win32/Networks.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Task/Inventory/Win32/Networks.pm), [Win32/Softwares.pm](https://github.com/glpi-project/glpi-agent/blob/develop/lib/GLPI/Agent/Task/Inventory/Win32/Softwares.pm)
- Fleet(검색 요약): hardware UUID 중복(복제 VM)으로 호스트가 서로 덮어쓰고 재등록 반복; `instance`로 바꾸면 기존 호스트가 중복 생성되어 정리 필요; Orbit 자동 업데이트와 동시에 호스트가 반복 삭제/재생성된 사례("unauthenticated, or invalid token") 원인 미확인 — [osquery Slack](https://chat.osquery.io/t/26904989/hi-all-i-m-trying-to-debug-a-situation-where-i-think-hosts-a), [osquery Slack 5089](https://chat.osquery.io/t/5089/hello-fleet-we-ve-been-seeing-a-lot-of-hosts-failing-to-enro)
- osquery `patches` 테이블은 MSI/Windows Update 경유 패치(서비스 팩 등)를 포함하지 않고, `windows_security_products`는 Windows Server 비호환 — [patches.table](https://github.com/osquery/osquery/blob/master/specs/windows/patches.table), [windows_security_products.table](https://github.com/osquery/osquery/blob/master/specs/windows/windows_security_products.table)
- Fleet 운영 제약: MySQL 단일 writer만 지원("Multi-writer or group-replication MySQL setups are not supported"), MySQL 9.6.0 비호환, 인스턴스당 DB 분리 시 추가 리소스 필요 — [Reference-Architectures.md](https://github.com/fleetdm/fleet/blob/main/docs/Deploy/Reference-Architectures.md)
- ConfigMgr(검색 요약): delta 불일치 후 resync 정책 할당 실패로 클라이언트가 동기화되지 않는 사례; 중복 하드웨어 ID(USB NIC) 등록 후에도 계정에 남는 사례 — [MS Q&A 1070067](https://learn.microsoft.com/en-us/answers/a/1070067), [prajwaldesai(2차)](https://www.prajwaldesai.com/?p=208328)
- Ralph는 2025-02부터 "Sources only" 모델("we do not guarantee responses to issues or support for pull requests") — [README](https://github.com/allegro/ralph/blob/ng/README.md)
- Snipe-IT는 서드파티 연동에 대해 "Snipe-IT cannot provide support for these project" — [README](https://github.com/grokability/snipe-it/blob/develop/README.md)

### Inferences
- 자체 서버(ASP.NET Core + MS SQL)에서 가장 먼저 설계해야 할 안전장치: 인벤토리 수신 큐(비동기 처리로 DB 락/폭주 분리), 장비 단위 처리 락, 블랙리스트(시리얼/MAC/UUID), 매칭 룰 우선순위 UI와 매칭 로그, 그리고 집계 테이블 사전 계산. OCS/GLPI의 운영 불만 대부분이 이 네 가지 부재에서 온다.
- XML 오버헤드 자체는 압축으로 완화되지만, 실제 병목은 파싱 후 섹션별 DELETE/INSERT(OCS `delOnReplace`)다. 행 단위 diff(OCS `INVENTORY_WRITE_DIFF`, GLPI partial)를 처음부터 지원하는 것이 낫다.

### Gaps
- GLPI 11 네이티브 인벤토리의 5,000대 이상 실측 성능 자료(처리 시간, DB 크기)는 찾지 못했다.
- Tactical RMM/MeshCentral/Wazuh의 대규모 운영 불만은 검색 한도 소진으로 조사하지 못했다.

## 7. 라이선스와 재사용 가능성 (에이전트 소스/프로토콜 문서)

### Takeaway
GLPI Agent·OCS(서버/에이전트)는 GPLv2(+)이고 GLPI 서버는 GPL 계열, Snipe-IT는 AGPLv3, Rudder는 GPLv3, Wazuh는 GPLv2 기반, osquery는 Apache-2.0 OR GPL-2.0 듀얼, Fleet는 MIT(단 `ee/` 디렉터리는 별도 상용 라이선스, docs는 CC BY-SA 4.0), MeshCentral은 Apache-2.0, Ralph는 Apache-2.0, Tactical RMM은 자체 "Tactical RMM License v1.0"(오픈소스 아님, SaaS 제공 제한). 따라서 **코드를 C#로 "포팅/복제"해 상용 사내 제품에 넣는 것은 GPL/AGPL 계열(GLPI Agent, OCS, Snipe-IT, Rudder, Wazuh)에서는 피해야 하고, 설계·프로토콜·스키마를 "참고"하는 것은 문제없다.** JSON 스키마(inventory_format)와 osquery remote API 사양은 사실상 프로토콜 문서로 자유롭게 참고 가능하며, osquery(Apache 선택)/Fleet(MIT)/MeshCentral/Ralph(Apache)는 코드 재사용도 가능하다.
